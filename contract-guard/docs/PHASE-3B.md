# ContractGuard — Phase 3B: Precise Blast-Radius Analysis & Deterministic Dependency Graph

## Overview

In **Phase 3B**, ContractGuard strengthens its deterministic blast-radius analysis to answer the core engineering question:

> **"What downstream code is actually affected by this API contract change?"**

Phase 3B enhances precision while remaining strictly bounded by the core architectural philosophy:

> **"AI reasons. Deterministic checks decide. Bob executes. Deterministic verification proves."**
>
> **"Confirmed means deterministic evidence exists. Likely means inference and must never be presented as confirmed."**

ContractGuard does **not** turn into a general-purpose static analyzer or Java compiler framework. It remains small, deterministic, explainable, and testable.

---

## 1. Core Principles & Design Boundaries

### The Conservative Evidence Model

ContractGuard adheres to a strict evidence hierarchy:

1. **Confirmed Impact (Facts)**: Only classified as confirmed when explicit deterministic evidence exists in the file (matching field tokens, accessors, annotations, or serialized fixture literals).
2. **Likely Impact (Inferred)**: Files matching endpoint call paths (e.g. `/api/payments/{id}` -> `PaymentClient`) without confirmed field-level references remain strictly categorized as **Likely**. They are **never** promoted to confirmed without deterministic proof.
3. **Contract-Only Consumers**: Consumers whose contracts reference the broken schema, but whose codebase contains 0 confirmed source or test file references, are explicitly identified as **contract-only consumers**.
4. **No Speculative Transitive Inference**: Transitive consumers are reported only if explicit multi-hop dependency edges exist in `contractguard.yaml` configurations. If no chained relationship is declared, `transitive_consumers: 0` is reported without guessing.

### Architectural Boundary Non-Goals

ContractGuard explicitly does **NOT** implement:
- Full Java compiler or bytecode parser
- Heavyweight Java/TypeScript AST frameworks
- Semantic code understanding using an LLM
- Arbitrary dependency inference from package names, imports, or file naming heuristics
- Database, Web UI, or AsyncAPI/GraphQL extensions
- Autonomous code editing (code execution and patching strictly belongs to IBM Bob)

## 2. Blast-Radius Precision Dimensions

| Dimension | Definition | Determination Rule | Example |
|---|---|---|---|
| **Direct Consumers** | Services that declare a direct dependency on the producer contract in `contractguard.yaml`. | Explicit configuration | `payment-client`, `order-service`, `reporting-service` (3) |
| **Affected Consumers** | Direct consumers whose contracts break due to producer changes. | Deterministic OpenAPI comparison | 3 |
| **Contract-Only Consumers** | Affected consumers with 0 confirmed source and 0 confirmed test files. | `confirmed_source == 0` and `confirmed_test == 0` | `order-service`, `reporting-service` (2) |
| **Confirmed Source Files** | Source files containing direct field references, accessors, or annotations. | Explicit token matches | `PaymentResponse.java`, `PaymentDisplayService.java` (2) |
| **Confirmed Test Files** | Test files or test fixtures containing confirmed field references or JSON keys. | Test path + explicit token match | `PaymentClientTest.java`, `PaymentResponseSerializationTest.java`, `PaymentDisplayServiceTest.java` (3) |
| **Likely Source Files** | Files matching endpoint path tokens without confirmed field matches. | Endpoint token match | `PaymentClient.java` (1) |
| **Transitive Consumers** | Downstream consumers reachable via multi-hop explicit edges (A -> B -> C). | Explicit graph traversal | 0 (in standard flat demo) |

## 3. Confirmed Source & Test Evidence Detection

When an API contract change occurs, such as:

$$\text{paymentAmount} \longrightarrow \text{totalAmount}$$

ContractGuard scans the consumer directory for explicit, deterministic references:

### A. Confirmed Source References
A source file is confirmed affected if its content contains at least one deterministic token generated by `_extract_field_tokens`:
- **Exact Field Tokens**: `paymentAmount`, `payment_amount`
- **Accessor Methods**: `getPaymentAmount()`, `setPaymentAmount()`, `isPaymentAmount()`, `get_payment_amount()`, `set_payment_amount()`
- **Serialization Annotations**:
  - `@JsonProperty("paymentAmount")`
  - `@JsonProperty('paymentAmount')`
  - `@SerializedName("paymentAmount")`
  - `@SerializedName('paymentAmount')`

### B. Confirmed Test References
Test files are identified by checking whether their path or filename includes:
- `"test"` in directory parts (e.g. `src/test/java`, `src/test/resources`)
- `"Test"` in file name (e.g. `PaymentClientTest.java`)
- `test_` prefix or `_test.py` suffix
- `"fixtures"` or `"fixture"` in directory parts (e.g. `src/test/resources/fixtures`)

If an identified test file or fixture contains any of the confirmed field tokens or literal quoted keys (`"paymentAmount"`), it is classified as **Confirmed Test Impact**.

### C. Likely Impact Mechanism
Likely tokens are derived strictly from endpoint path segments (via `_extract_likely_tokens`):
- Endpoint path `/api/payments/{id}` yields path tokens: `payments`, `Payments`, `payment`, `Payment`.
- Files matching these endpoint tokens in their text content, but **not** containing confirmed field tokens, are categorized as **Likely**.
- In the reference demo, `PaymentClient.java` invokes `/api/payments/` but does not reference the DTO field `paymentAmount` directly, so it is deterministically classified as **Likely Source**.

### D. Confirmed vs. Likely Separation (Reference Workspace)
```text
CONFIRMED SOURCE:
  - src/main/java/com/example/paymentclient/model/PaymentResponse.java       (defines paymentAmount, getPaymentAmount)
  - src/main/java/com/example/paymentclient/service/PaymentDisplayService.java (calls getPaymentAmount())

CONFIRMED TEST:
  - src/test/java/com/example/paymentclient/client/PaymentClientTest.java
  - src/test/java/com/example/paymentclient/model/PaymentResponseSerializationTest.java
  - src/test/java/com/example/paymentclient/service/PaymentDisplayServiceTest.java

LIKELY SOURCE:
  - src/main/java/com/example/paymentclient/client/PaymentClient.java        (matches endpoint /api/payments, 0 field references)

CONTRACT-ONLY CONSUMERS:
  - order-service     (breaking schema diff in contracts/payment-service.yaml, 0 source/test references)
  - reporting-service (breaking schema diff in contracts/payment-service.yaml, 0 source/test references)
```

## 4. Deterministic Dependency Graph

Implemented in [`src/contract_guard/graph.py`](../src/contract_guard/graph.py):

### Data Models
- **`DependencyNode`**: Represents a service node, its base repository path, associated contracts, and role (`is_producer`, `is_consumer`).
- **`DependencyEdge`**: Represents an explicit directed relationship (`producer`, `consumer`, `contract`, `relationship_type="direct_consumer"`).
- **`DependencyGraph`**: Queryable in-memory representation providing:
  - `get_direct_consumers(producer: str) -> list[str]`
  - `get_transitive_consumers(producer: str) -> list[str]`
  - `render_tree(root_service: str | None = None) -> str`
  - `to_dict()` and `to_json()`

### Authoritative Graph Principles
- The dependency graph is constructed from explicit `contractguard.yaml` declarations.
- Fully deterministic sorting of nodes, edges, and contract lists.
- Duplicate edges are deduplicated automatically.
- No AI inference, package scanning, or heuristic guesswork.

### CLI Usage: `contract-guard impact`

The `impact` command supports `--format text`, `--format json`, and `--format markdown`.

#### Text Format (`--format text`)
```text
CONTRACTGUARD — BLAST RADIUS

API CHANGE
paymentAmount -> totalAmount

3

AFFECTED CONSUMERS
3

CONTRACT-ONLY CONSUMERS
2

CONFIRMED SOURCE FILES

CONFIRMED TEST FILES
3
  - src/test/java/com/example/paymentclient/client/PaymentClientTest.java
```


## 6. MCP Integration

ContractGuard extends the existing `get_blast_radius` tool without increasing the tool count or altering backward-compatible payloads:
- Exposes `dependency_graph` containing nodes, edges, and counts.
- Enriches `blast_radius_summary` with `direct_consumers`, `contract_only_consumers`, and `transitive_consumers`.
- Preserves all existing keys (`affected_services`, `confirmed_source_files`, `confirmed_test_files`, etc.).

## 7. Repair Mission Integration

Phase 3A's `RepairMission` consumes Phase 3B's enriched blast-radius data:
- `AffectedConsumerMission` preserves existing confirmed lists (`confirmed_source_files`, `confirmed_test_files`).
- Exposes `likely_source_files` and `likely_test_files` explicitly separated from confirmed evidence.
- Preserves the invariant: **No Invented Source Files**.
